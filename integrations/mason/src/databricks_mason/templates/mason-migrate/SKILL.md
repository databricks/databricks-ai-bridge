# Migrate an existing LangGraph or OpenAI Agents SDK agent to Mason

Integrate Mason so its commands work through the same integration points as the bundled template
for the project's framework. Preserve the existing agent and application contracts. Configuration
alone does not complete migration.

## Inspect the project and reference

Read `references/migration.json` for the server, bundled template version, chat-app choice, and
optional profile. It names the `framework` the reference was generated for; the migration follows
that framework's runtime semantics. `references/template/` is a candidate project generated
from the templates shipped with the installed CLI. Use it as migration evidence, not an importable
application dependency.

Read [the shared Mason contract](references/template/MASON_CONTRACT.md). It is written for the
named framework — LangGraph or OpenAI Agents — and its runtime requirements apply as written.
Then inspect adjacent template code for the integration points being adapted. If the chat app is
enabled, also read `references/template/CHAT_APP.md` and inspect `runtime/ui.py`. The contract owns
runtime requirements; this skill owns migration decisions.

Locate agent construction, state and history handling, model/tool wiring, persistence, invocation
config, interrupt/resume handling, HTTP serving, authentication, and tests. Identify
package/import conflicts with the reference. Explain the concrete changes, then implement them.
Preserve the agent's model, prompts, structure, tools, routing, and approval policy unless a
change is required and accepted.

## Explicitly handle existing state and contracts

State and durability semantics differ by framework; handle the ones that apply:

- **LangGraph:** checkpointer, thread IDs, checkpoint namespaces, graph state, reducers,
  subgraphs, and pending interrupts. Runtime recovery may resume a checkpoint belonging to the
  current invocation; otherwise original input replays.
- **OpenAI Agents SDK:** the `Session` transcript is the persistent conversation state. There is
  no checkpoint continuation; recovery replays the persisted application input against the same
  session. HITL `RunState` is process-local and does not survive worker loss even with a Session
  Store bound.

- **Persistence and history:** Identify the current checkpointer or session store, memory store,
  thread/session IDs, actor/tenant mapping, and pending interrupts or approvals. Switching stores
  does not migrate checkpoints, transcripts, or memories. Preserve access to existing history
  until the transition is decided. Do not silently reset state, delete storage, or claim old
  conversations were migrated. Surface choices about copying history, starting new threads or
  sessions, or retiring storage.
- **Custom state and outputs:** Preserve fields, reducers and subgraphs where the framework has
  them, structured inputs/outputs, streaming events, and interrupts or approval flows. The
  reference assumes message-oriented events and is not a generic serializer. Implement explicit
  mappings without discarding custom results to fit the reference UI.
- **Identity and sessions:** Preserve authentication, actor/tenant isolation, and session/thread
  identity. The reference separates invocation UUIDs, application session IDs, and the routing
  cookie. Map existing IDs explicitly, including reopening sessions. Derive actor identity from
  the trusted application context; do not blindly trust a caller field or adopt a shared
  fallback. If the existing server used a different request/response shape (e.g. a
  `{conversation_id, message}` body), map it explicitly in `runtime/adapter.py` to Mason's
  `input.session_id` / `input.messages`, and preserve response fields clients depend on.
- **Recovery and durability:** Distinguish Runtime Store invocation recovery from Session Store
  persistence. Address at-least-once side effects and retain stronger existing guarantees. Do not
  silently enable replay of non-idempotent tools.

## Implement the shared contract

Implement the command requirements in `references/template/MASON_CONTRACT.md`, using the template
as an example. Merge candidate `agent.toml`, `.mason/project.toml`, dependencies, and startup config
without overwriting existing choices. `mason init --existing` writes these manifests only inside
`references/template/`, not into the project, so copy or merge them to the project root; default
store names come from the reference's generated `agent.toml`. Candidate stores are migration
intent, not authorization to provision resources or switch live state. Use `uv` and the bundled
template's compatible Mason dependency. Migration may raise the project's minimum Python version:
the templates require `>=3.11` (the runtime uses 3.11+ features such as `asyncio.timeout`). Check
and bump `requires-python` and CI accordingly.

Keep framework-native execution independent of Mason request/context types. Adapt package
conflicts and preserve tool execution and approval logic. Merge run configuration without losing
callbacks, run limits, configurable fields, or session/checkpoint settings. Preserve existing
tracing when composing Mason tracing.

Reuse the HTTP server where feasible. Follow the contract's distinction between basic CLI launch
requirements, Mason `DurableAgentServer` hooks, and optional chat UI mappings. Adapt the UI only when
selected. Do not copy sample tools, models, prompts, or business logic into the application.
Model provider is a migration decision: keep the existing one or adopt the gateway; the
reference example is not mandatory.

## Verify and hand off

Run existing tests and relevant lint/type checks. Add focused offline regression tests for custom
inputs/outputs, streaming, remote and local tool wiring, store selection, actor/session isolation,
interrupt/resume and approval flows, and invocation recovery where used. Use fakes for remote
services. Confirm the configured entrypoint starts with the project's test setup.

Do not provision, deploy, make live model/tool calls, or run integration tests unless authorized.
Run `mason doctor .` after the migration and resolve every failed check. Doctor is a read-only,
offline verification step; it does not replace the focused runtime and contract tests above.

Report changes, validation, unresolved state or client-contract decisions, and readiness for
`dev`, `tools add`, `sessions bind`, `memory bind`, tracing, `endpoint`, and `deploy`. Distinguish
local wiring from live validation. Exclude the reference snapshot from application packaging and
test discovery if the project would otherwise collect it.
